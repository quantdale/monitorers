## Why

Two changes — `fix-history-emission-rate` (task 8.7) and `add-realistic-usage-test-suite` (task 5.5, which absorbed 8.7) — are each one checkbox from complete. That remaining checkbox is the **same** task in both: a manual end-to-end verification that, in the real running app, the "1 hour" window tracks real elapsed time 1:1 (the COR-001 fix holds at runtime) and CPU/GPU readouts still update multiple times per second (liveness preserved). Both changes mark it *"not automatable — requires an interactive Windows session with real hardware sensors."*

That verdict was written from a **Linux sandbox** with no Win32 sensors. It conflates two separable blockers:
1. **Environment** — needs real PDH/WMI/NVML hardware. (Gone: this now runs on real Windows dev machines.)
2. **Human observation** — "watch a GUI with a stopwatch," "eyeball the numbers changing." (Still present — nothing captures the runtime signal for a machine to check.)

The `fix-history-emission-rate` change already made the signal machine-readable as a side effect: every `metrics-update` event now carries `on_tick: bool` (schema v3) — ground truth for *"was this a history-committing (1 Hz) tick."* The missing piece is **tooling that taps the real event stream and asserts the cadence invariants**, so an AI agent (or CI on a self-hosted Windows runner) gets a PASS/FAIL instead of a human needing a stopwatch.

This is not a throwaway checkbox-closer. COR-001 (frontend history growing at 4 Hz instead of 1 Hz) is a bug class that has **already recurred twice** — once on the Rust side (`1c30a6c`), once on the IPC/frontend side (`fix-history-emission-rate`). A probe that exercises the *real* emission cadence end-to-end is the regression guard that stops a third recurrence, at a layer the existing pure-unit tests (`is_full_poll_tick`, `shouldCommitHistory`) cannot reach — they test the *gate in isolation*, never the *assembled loop against real I/O*.

## What Changes

- **Refactor (behavior-preserving): make the collector tick loop sink-agnostic.** Extract the tick-loop body currently inlined in `main.rs`'s `setup()` closure (`main.rs:452–499`) into a reusable function that takes an **emit sink** (a closure/trait for delivering each `MetricsSnapshot`) and an **error sink** (for the `collector-error` message), plus an optional **bounded tick count** (`None` = run forever, as production does; `Some(n)` = run n ticks and return). Production passes a sink that calls `app_handle.emit("metrics-update", …)` — identical observable behavior, same `catch_unwind`/panic-break semantics, same 250ms cadence, same one-`PdhCollectQueryData`-per-full-tick invariant. The store dependency is taken as `&SafeHistoryStore` rather than pulled from `app_handle.state::<…>()`, so the loop no longer requires a Tauri `AppHandle`.
- **New tooling: a headless cadence probe.** A small binary (`src-tauri/src/bin/cadence_probe.rs`) that constructs a real `CollectorState` (hardware detection + PDH open + WMI connect on an MTA thread, mirroring production's startup), runs the extracted loop for a bounded duration with a recording sink, and streams one JSONL record per emitted snapshot to stdout: `{ "elapsed_ms": u64, "on_tick": bool, "cpu_len": usize, "gpu_total_len": usize, "ts_len": usize }`. Built with default features (`nvapi`, `nvml`) so it exercises the same code path as the shipped app.
- **New tooling: a cadence checker.** A checker (Rust integration test, `#[ignore]`-gated as a real-hardware test, plus a thin standalone entry the agent can run directly) that consumes the JSONL and asserts the two invariants: (A) mean inter-emit period ≈ 250 ms within tolerance → liveness; (B) `on_tick:true` cadence ≈ 1 Hz, history length grows by exactly +1 per `on_tick:true` record and +0 per `on_tick:false` record, and total history length ≈ elapsed whole seconds → fidelity/no drift. Emits a human- and machine-readable report and a nonzero exit on failure.
- **Optional dev tap (Layer 2 confirmation).** An env-gated (`SYSMON_CADENCE_LOG=1`) stderr line per emit in the production sink, so the agent can also launch the *full* `npm run tauri dev` app (real webview + real frontend `shouldCommitHistory` gating), let it run ~90 s, and run the same checker against captured stderr — confirming the assembled app agrees with the headless probe. Off by default; zero cost when the env var is unset.
- **New agent runbook.** A short documented procedure (`docs/` or the change's tasks) an AI agent follows to run the probe, run the checker, interpret PASS/FAIL, and — on PASS — check off the two absorbed manual tasks with the captured report as evidence.
- **Supersede the manual gate.** Update `fix-history-emission-rate` task 8.7 and `add-realistic-usage-test-suite` task 5.5 to reference this change's automated procedure as the fulfilling mechanism (the manual stopwatch run becomes optional, not required).

## Capabilities

### Modified Capabilities
- `metrics-history-streaming`: adds requirements that the collector loop be sink-agnostic (runnable headless without an `AppHandle`) and that the 1 Hz-history / 4 Hz-liveness cadence be **autonomously verifiable against real hardware** via a bounded probe + checker, not only by manual observation. The existing 1 Hz/4 Hz behavioral requirements are unchanged; this formalizes their *verifiability*.

## Impact

- **Code**: `src-tauri/src/main.rs` (extract tick loop behind sinks; env-gated dev tap in the production sink), a new `src-tauri/src/bin/cadence_probe.rs`, a new checker (Rust integration test + standalone runner), possibly a small `src-tauri/src/collector/probe.rs` or `lib`-level re-export so the loop is reachable from both `main` and the bin. No change to `MetricsSnapshot` shape, `SCHEMA_VERSION`, the 250ms cadence, or the 4-tick ratio.
- **Tests**: Rust test count grows (checker assertions, sink-extraction unit tests). The real-hardware probe test is `#[ignore]`-gated so the default `cargo test` count and CI (which may lack sensors) are unaffected until run explicitly on a sensor-equipped runner.
- **Scope boundary**: this change automates verification of the **emission cadence** (the source of truth). It does **not** stand up a browser/webview driver to assert the literal *rendered* number changing or the *DOM* chart point count — that is Layer 3, deferred to the separate phased change `add-e2e-verification-harness`. The frontend `shouldCommitHistory` gating and the `MAX_HISTORY=3600` ring-buffer wrap remain covered by their existing unit tests (`add-realistic-usage-test-suite` tasks 6.1/6.2, `fix-history-emission-rate` task 7.1).
- **Out of scope**: auto-restart of the collector on panic (ARC-002), any change to the collection strategy, and the general E2E driver framework (its own change).
